# go-async-jobs V2 — isolated scheduling and observability

**This is the independent [go-async-jobs-v2](https://github.com/gamaheshwari246/go-async-jobs-v2) repository.** V1 is maintained separately, and its live DigitalOcean deployment is unaffected.

See [design assumptions](docs/ASSUMPTIONS.md), [active technical debt](docs/TECHNICAL_DEBT.md) and [resolved P1 issues](docs/RESOLVED.md). Delayed requests now replay safely after `run_at`, and multiple scheduler replicas deduplicate matching UTC occurrences.

## What's new

1. **Delayed jobs** — `POST /jobs` accepts `run_at` as an RFC3339 timestamp (with timezone), later than the current time and no more than 30 days ahead. Asynq's `ProcessAt` schedules the task, with the worker polling scheduled tasks every second. The response is `202` with `status: "scheduled"` and `run_at`. A scheduled task reports `scheduled` through `GET /jobs/{id}`. This is a *not-before* guarantee, not exact-time execution under load.
2. **Recurring jobs** — standalone, independently scalable `scheduler` Compose service (profile `scheduler`), configured using `CRON_SCHEDULE`, `CRON_TASK_TYPE`, `CRON_PAYLOAD`, `CRON_PRIORITY`. Uses Asynq Scheduler and UTC. Default is one `demo.sleep` task per minute. Multiple scheduler replicas coordinate per occurrence through deterministic Redis/Asynq task IDs, preventing duplicate enqueues while the task ID is retained. Cron configuration is static: restart the scheduler to change it. This is not a REST-managed persistent per-user schedule API.
3. **Prometheus-compatible metrics** — new **admin-authenticated** `GET /metrics` route exports per-queue waiting/active gauges, task-attempt duration histogram, attempt counters by outcome, retry-exhausted DLQ counter, worker heartbeat count, total worker concurrency slots, and approximate worker utilization. Aggregation uses Redis, so horizontally scaled workers contribute to the same metrics.

### Run V2 locally without disturbing V1

From the same GitHub repo, on a **separate checkout**:
```bash
git clone https://github.com/gamaheshwari246/go-async-jobs-v2.git
cd go-async-jobs-v2
docker compose --profile scheduler up --build -d --scale worker=2
docker compose ps
curl http://127.0.0.1:8080/readyz
```

V2 Compose has a **separate project name and Redis volume**. It publishes API port **8080** on all host interfaces for the cloud demo; **stop V1 before starting V2** to avoid the port conflict. Limit inbound TCP 8080 to your own public IP with the DigitalOcean firewall because job submission is unauthenticated. The scheduler profile starts one replica by default. You can scale it to multiple replicas; deduplicated UTC ticks enqueue at most one logical task per retained occurrence.

### Schedule a future job

```bash
RUN_AT=$(date -u -d '+45 seconds' +%Y-%m-%dT%H:%M:%SZ)
curl -s -X POST http://127.0.0.1:8080/jobs -H 'Content-Type: application/json' \
  -d "{\"type\":\"demo.sleep\",\"priority\":9,\"payload\":{\"duration_ms\":100},\"run_at\":\"$RUN_AT\"}"
```

Record `job_id` and query `GET /jobs/{id}`. Before execution it reports `scheduled`; after it reports `succeeded`.

### Scrape observability metrics

`GET /metrics` requires `Authorization: Bearer <ADMIN_TOKEN>`. The default Compose development token is `local-dev-token`; **replace it before network exposure**. Example from the Droplet localhost:

```bash
curl -fsS -H 'Authorization: Bearer local-dev-token' http://127.0.0.1:8080/metrics
```

PromQL examples:
```promql
# Task processing-attempt latency, rolling five-minute p50/p95.
histogram_quantile(0.50, sum by (le) (rate(go_jobs_attempt_duration_seconds_bucket[5m])))
histogram_quantile(0.95, sum by (le) (rate(go_jobs_attempt_duration_seconds_bucket[5m])))
# Terminal failures / second, across worker replicas.
sum(rate(go_jobs_dead_lettered_total[5m]))
# Live worker-slot utilization is exported as go_jobs_worker_utilization.
```

The histogram measures **processing-attempt latency**, not queue wait or whole-job end-to-end latency. Percentiles require Prometheus or another histogram-aware query engine; instantaneous p50/p95 are not emitted as text gauges. Dead-letter rate tracks **retry exhaustion** via the Asynq error callback and is best effort. Worker utilization is active tasks divided by live advertised slots (heartbeats expire after 20 seconds), not CPU utilization.

Telemetry writes are intentionally best effort: metrics cannot fail business tasks. Metrics are kept in Redis and will be lost if Redis data is discarded. Under memory pressure the telemetry writes can fail and metric counts can under-report; Redis monitoring remains necessary.

### Multi-replica cron safety

```bash
docker compose --profile scheduler up -d --no-deps --scale scheduler=2 scheduler
docker compose logs --since=2m scheduler | grep -E 'cron_enqueued|cron_tick_deduplicated'
```

Each matching scheduler replica computes the same UTC schedule/tick task ID. Duplicate enqueue attempts are rejected by Asynq while the record exists (48-hour completed-task retention). This is **not exactly-once business processing**, and missed ticks while **all** scheduler replicas are offline are not automatically backfilled. See [TD-005](docs/TECHNICAL_DEBT.md).

### Idempotent delayed retry after deadline

A matching, retained `Idempotency-Key` replay returns the original job ID even when its `run_at` has passed. A new request with a past `run_at` is still HTTP 400, a conflicting key is HTTP 409, and a committed-but-expired task is HTTP 410.
